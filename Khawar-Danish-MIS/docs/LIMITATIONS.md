# Scope and remaining work — version 0.1

This release is an **implementation baseline**, not acceptance-complete software. The supplied specification remains the target, not a statement of delivered functionality. Source implementation and runtime verification are different. All PHP/database workflows below remain unexecuted in the build environment.

## Material gaps to resolve before production

1. **Runtime verification:** no PHP executable, MySQL/MariaDB server or Chromium executable was available. PHP syntax lint, PHP tests, database integration, Windows installation, browser interactions and print layouts have not been run. Lexical/static checks cannot substitute for these.
2. **Bootstrap:** no Bootstrap 5 package is bundled. The UI uses original responsive CSS with local DejaVu Sans. No remote dependencies were substituted. A Bootstrap-based layout is still required to meet the original technology requirement.
3. **Branding/uploads:** center text settings exist; logo upload, student photographs and identity-document fields are not implemented. Backup includes future eligible immutable image files, but there is no upload interface.
4. **Academic model:** programs contain subjects through their running class assignments, not a reusable program-subject template. The `required` flag is stored but does not implement optional subject selection. Every enrolled student is included in every class subject. Independently priced subject enrollment and subject-specific percentage compensation are not implemented.
5. **Attendance:** one status per enrollment/class-subject/date. Multiple meetings of the same subject on one day share that record. This is **daily attendance**, not distinct session attendance. No teacher attendance. Holidays and nonscheduled dates are marked in the register, but makeup attendance may be entered. Late counts as present for alerts; unrecorded days are excluded. This must be explained to staff to avoid misleading rates.
6. **Scheduling/assignments:** no edit/end/cancel UI for timetable entries, and class-subject assignments are immutable. Create-only scheduling cannot yet support ordinary teacher replacements and recurring timetable changes safely. Teacher/room filters are not implemented as dedicated timetable controls. Friday closure does not suppress the normal weekly schedule in the dashboard; the monthly register marks it.
7. **Exams/documents:** weighted results are per subject only, with no ranking, consolidated multi-subject result card or exam-aware enrollment date filtering across the entire class history. Completion certificate requires manually completed enrollment, not automatic pass/fail eligibility. Certificate wording is manually entered; no visual template editor. Enrollment confirmation and dedicated salary statement templates are missing. Browser printing is supplied but actual RTL, clipping, pagination and A4 acceptance are unverified. Certificate print counts require a manual “record print” action, and do not count arbitrary browser prints.
8. **Financial corrections:** receipts/refunds/payroll payments are idempotent and immutable in source. General movements can be reversed; credits, mistaken allocations, receipt dates, payroll approvals and salary payments do not yet have full corrective workflows. There is no cancellation UI for an erroneous charge; an authorized credit can cancel its unpaid amount. Do not compensate for missing correction workflows by editing DB rows. These are significant production blockers.
9. **Payroll:** agreements are class-level and immutable. Fixed salary must be manually split between class agreements or it will be counted for each agreement. Only fully closed Gregorian months can be approved; approval is immediate (no separate draft persistence). No automatic recovery of negative payroll balances already paid; later net payable caps take account of approved negative totals, but staff must resolve employee recoveries explicitly. Snapshot detail is technical JSON rather than a fully localized explanation table. Allocation percentage/refund rounding requires edge-case runtime tests.
10. **Finance/reporting:** monthly fees/installments are entered as separate manual charges; no automatic charge generator or installment wizard. Discounts are credits against unpaid charges only. Opening balances are undated and immutable. Reconciliations document discrepancies but do not resolve them automatically. Category names are free text. Other staff salaries are general expenses. No accrual P&L. Class collection report is gross receipt allocations; refunds are separate. Current receivables are not historical as-of receivables. CSV export is limited to the cash summary.
11. **Usability/data volume:** master lists have name search and 25-row pagination. Several transaction lists show only the latest 100/200 rows; some selectors and reports load all matching rows. No tested large-dataset performance, broad filtering or report pagination. Some raw stored status values/technical audit details appear in English. Not all form values survive validation errors. Validation messages are generic in places. No inactivity warning countdown or global password-change UI for ordinary users.
12. **Security/operations:** role action enforcement is in the front controller, with teacher scoping on class operations. Custom roles require careful assignment of a teacher profile to obtain teacher-specific scope. No third-party security audit, penetration test or live direct-route permission test has been executed. Printer permissions govern app controls; they cannot prevent a user printing information already visible in a browser. Backups are unencrypted. No scheduled backups; restore is local CLI only, with a 128 MiB uncompressed limit. Restore integrity checks are not authenticity signatures.
13. **Existing-data migration:** this is a new project because only the specification text was attached in this task. No old project ZIP was inspected, no old schema was mapped, and no legacy records were migrated. Never point it at an existing course-management database without a reviewed migration.
14. **Updates:** schema version 1 and install refusal guard exist. No automated migration runner or delivered upgrade from a previous schema. Future SQL migrations must be reviewed and executed sequentially on a backed-up test copy first.

## Suggested completion order

1. Install into an isolated Windows test environment and run lint/unit/DB tests; fix every failure.
2. Run the manual acceptance checklist, including adverse financial cases and direct-route authorization.
3. Finish financial reversals, assignment/schedule changes and the required academic model.
4. Finish localization, Bootstrap/local branding assets and documents; inspect both-language printouts.
5. Test backup/restore to a separate installation; test multiple staff sessions and performance.
6. Only after acceptance, prepare any legacy migration with before/after record counts and financial reconciliation.

No production readiness, complete feature coverage, successful PHP execution or successful restoration is claimed for this package.


به‌روزرسانی تقسیم اوقات، حاضری و شاگردان — ۷ عقرب ۱۴۰۵

تقسیم اوقات: روزهای یک مضمون با ساعت، اتاق و تاریخ یکسان در یک سطر نمایش داده می‌شود. روزهای هفته در همان سطر نوشته می‌شود؛ بررسی تداخل هر روز همچنان جداگانه صورت می‌گیرد.
حاضری: در حاضری ماهانه و ورق چاپی، زیر شماره هر روز نام روز هفته نیز درج می‌شود. تعداد روزها مطابق ماه انتخاب‌شده است.
تقدیرنامه و تصدیق‌نامه تکمیل دوره: متن تقدیر یا تکمیل دوره انگلیسی نیز همراه متن فارسی چاپ می‌شود. برای نام انگلیسی شاگرد و دوره، املای لاتین را هنگام ثبت معلومات وارد کنید؛ سیستم نام اشخاص را ترجمه نمی‌کند.
شاگرد فعال: حداقل یک ثبت‌نام فعال دارد که تاریخ امروز در محدوده ثبت‌نام و دوره فعال باشد. پس از ختم آخرین دوره یا قطع ثبت‌نام، خودکار در فهرست غیر فعال قرار می‌گیرد. ثبت‌نام مجدد در یک دوره جاری او را دوباره فعال می‌سازد. پرداخت پول به تنهایی وضعیت فعالیت را تعیین نمی‌کند. شاگرد تازه که هنوز شامل دوره نشده یا فقط دوره آینده دارد، فعلاً غیر فعال است. تعداد و فهرست هر دو گروه در صفحه اول، از «نمایش فهرست»، قابل مشاهده است. وضعیت اداری آرشیف‌شده مانع فعالیت است.
معاش ثابت استاد: مبلغ ثابت قرارداد مبنای ۳۰ روز دارد. مبلغ قابل پرداخت = مبلغ ثابت ÷ ۳۰ × روزهای تقویمی تحت پوشش قرارداد در ماه. مثال: معاش ۳۰۰۰ افغانی برای ۲۸ روز = ۲۸۰۰، برای ۳۰ روز = ۳۰۰۰ و برای ۳۱ روز = ۳۱۰۰ افغانی. قرارداد نیمه‌ماه فقط به تعداد روزهای شامل قرارداد محاسبه می‌شود. مبالغ قبلاً تأییدشده تغییر نمی‌کند. دوره محاسبه معاش مطابق بخش معاش، ماه میلادی است. این تغییر مربوط معاش اساتید است.
